Procedures

Assets

Live data

Asset Reliability Information Assistant, a maintenance and HSE assistant for a refinery. Answers procedure questions, looks up equipment, reads tank levels, raises and closes work orders. We picked a safety-adjacent domain deliberately. It makes the cost of every shortcut concrete: a hallucinated isolation procedure isn't a bad demo, it's an incident. The modern agent

LEFT SIDE: the loop itself. Request comes in, the model picks an ACTION, the tool returns an OBSERVATION, repeat until there's a Result. That's ReAct, and it's essentially every production agent once you strip the branding. It has been the same shape for a while. RIGHT SIDE: this is what actually changed, and it's where all the engineering is. Four categories: EXECUTION ENVIRONMENT: filesystem, sandboxes. Somewhere for the agent to do work that isn't your context window. CONTEXT MANAGEMENT: skills, memory, summarization, context offloading, prompt caching. Everything here is about what the model sees on this turn. Module 2's Level 0 tests assert on exactly this: what actually got assembled. STEERING: human-in-the-loop. Our `request_equipment_shutdown` gate. DELEGATION: planning, subagents. The `write_todos` tool and the `task` tool. THE POINT TO MAKE: the loop is the easy part, and it's not where your reliability comes from. Everything on the right is code you own and can test. Deep Agents ships most of the right-hand column already wired, planning, a filesystem, subagents, compression. That's why we build on it rather than assembling this ourselves.

Design for workflows over capabilities

Every tool we have

…now what?

Workflows we’ll ship

Look up

Raise work

Close out

Practice 0: before you write any code. START BY BEING FAIR TO THE INSTINCT. When we design agents we naturally think about everything the agent COULD do, and reach for giving it all the tools. That comes from good product sense, you're trying to make it capable and useful. It is not a dumb impulse. But it puts the reasoning the wrong way round. You end up with a pile of capabilities and no clear answer to "what does this actually do for someone on shift." You demo it, a planner says "that's neat, but it doesn't do the thing I need," and you find out about the workflow you should have supported after you've built the one you could. THE FLIP: think about the actual workflows it's going to enable, and specifically WHICH ONES YOU WANT TO SHIP WITH. Three is fine. Then fit the capabilities to those, rather than throwing the kitchen sink in. Two things fall out of that, both of which you can see in this repo: - `list_work_orders` exists because a workflow needed it ("close out that pump work order I raised earlier"), not because a tool was looking for a use. - Fewer tools is also cheaper and more reliable, every tool schema is tokens on every single turn, and more tools means more chances to pick the wrong one. Next slide is how you write those workflows down so they're executable.

Separate your concerns

Application

properly tested API

Agent

harness · model

keep it thin

Practice 1. When your agent gives a wrong answer there are four candidates: the context was wrong and misled the model, a tool errored or returned something misleading, the harness misbehaved, or the model reasoned badly. Only the last one is non-deterministic, slow, and expensive to test. The first three are ordinary software, IF you set the codebase up so they can be tested. If you can't rule those three out cheaply, EVERY debugging session investigates all four, and they're not independent, because bad tool output causes bad reasoning. So: application logic in its own package, with its OWN TEST SUITE, exposed over MCP. aria_mcp/ has no langchain import anywhere in it, but the thing to say out loud is not "no LLM," it's "properly tested API." Absence of an LLM is trivially achievable and worth nothing on its own. What earns you the boundary is that the left-hand box has tests you trust, so you can take it off the suspect list. Note the order on the slide: the application comes FIRST. You build and test that surface, then you point an agent at it. Teams that do it the other way round end up with business logic smeared across a system prompt. Four reasons for the protocol boundary specifically: 1. It forces the separation to be real, no reaching into agent state. 2. Independently testable and deployable. It's a service. 3. One application, many consumers, this agent, another agent, an IDE, a human. 4. A place to enforce authorization, where it can be audited. AND THE PAYOFF, which is worth saying out loud here: run `pytest tests/ -q` live. The whole application suite goes green in about six seconds with no API key and no model call. That means when ARIA misbehaves you get to say "the tools are correct" and mean it, with a green run behind you. The only remaining variable is the model. That's the prize, not the number of tests.

Design tools for agent consumption

A user asks about “P-101”. The real pumps are P-101A and P-101B.

pump lookup tool v1 returns {}
agent says “That equipment doesn’t exist.”

pump lookup tool v2 returns “Tags starting with P-101: P-101A, P-101B”
agent does retries with P-101A

THE highest-value 90 seconds in Module 1. Run get_equipment("P-101") against both. The framing: every rule below is a case where the CORRECT design for a human caller is the WRONG design for a model. Returning [] for no match is textbook API design. It is also how you get a confidently lying agent. Your caller changed; the rules changed with it. A user asks about "P-101". The real pumps are P-101A and P-101B, an A/B pair, like every critical pump in a refinery. v1 returns {}. The model reads that as "that equipment doesn't exist" and tells the user so, with total confidence. A technically-correct API produced a lying agent. No exception raised. Nothing in your error logs. Dashboards green. v2's error NAMES THE FIX. The model reads "P-101A, P-101B", picks one, recovers inside the same turn with no human involved. The takeaway, and say it in these words: write your error messages for the model that will read them. THEN GENERALISE VERBALLY: five rules for an API whose caller is a model. Say these over the slide; they don't need their own slide: 1. An unknown identifier is an ERROR, not []. Empty reads as "doesn't exist". 2. Errors CARRY THE FIX. That's what's on screen. 3. Output is BOUNDED. Unbounded tool output is a context-window incident waiting for your largest customer. 4. Output is DETERMINISTIC: stable sort order, or your evals flake for reasons that have nothing to do with the model. 5. PROVENANCE travels with the data. Every procedure we return carries its id, revision and a pre-formatted citation. You cannot evaluate groundedness if there is nothing to be grounded in. And a sixth that earns a sentence: BUSINESS RULES GO IN CODE. Tank T-043's gauge is flagged suspect, so its level must not be quoted as fact. v1 hands the model raw JSON and hopes it notices. Often it does, and "often" is not a safety property. It degrades silently on a model upgrade. v2 computes `data_quality_warnings` in tested code. Anything you can compute, compute; don't ask the model to notice.

Middleware guarantees.

Practice 2, and the highest-leverage idea in the module. "Always cite the procedure id and revision" in a prompt: measured at about 90%. That's one unsourced safety answer in ten. "Never show your reasoning": the model isn't leaking on purpose, so asking nicely doesn't address the cause. "Use at most 4 tool calls": it cannot reliably count its own tool calls. Every one of those is a middleware in v2, a guarantee instead of a request. And you stop paying for it in tokens on every single turn. The tell: ARIA v2's system prompt is SHORTER than v1's, and more reliable. Heuristic: if a rule can be expressed in code, it belongs in a hook. And go shopping in the built-ins first. Set limits

No cap

Infinite loops

Capped

Controlled costs

Practice 3. Non-negotiable, first thing to add to any agent. ModelCallLimitMiddleware(run_limit=25, thread_limit=120) ToolCallLimitMiddleware(run_limit=40, thread_limit=200) run_limit is per invocation; thread_limit is across a conversation and needs a checkpointer. A confused agent in a retry loop is not hypothetical. The usual trigger is a tool returning something the model reads as "almost worked, try again", which is exactly what v1's return "{}" creates. THE TWO PITFALLS COMPOUND: a bad API surface makes the runaway loop likely; no limit makes it unbounded. Without a cap, the ceiling on your spend is your provider's rate limit. You find out from Finance. Set them GENEROUSLY. The goal isn't to constrain normal behavior, a job package legitimately takes a dozen model calls. It's to make the pathological case terminate. A limit at 3x your p99 costs nothing and caps your downside.

New models every day

Practice 4: model choice. This one ANIMATES; let it loop at least twice before you start talking, then talk over it. Two axes: capability up, price to the right, and note the x-axis DOUBLES at each gridline. So one step left is half the cost. THE HEADLINE IS THE MOVEMENT. Watch the frontier sweep up and to the LEFT as the timeline runs. You get more capability for less money roughly every six months. The dashed lines left behind are where the frontier sat in Jul 25 and Jan 26. Say it plainly: a model choice you made a year ago is not the choice you would make today, and nobody goes back to check. READ THREE POINTS OFF IT: - Claude Opus 5, top right. Most capable, and you pay for it. - GLM 5.2 sits ON the frontier at a fraction of the price, open-weight, strong on tool use. Don't take the frontier on faith. Don't take US on faith. Measure it on YOUR dataset.

If you must have a scale, anchor every number

When you finally reach for a judge, the instinct is to ask it for a quality score out of ten. Resist it. "quality: 6/10" is unactionable. It doesn't say what was wrong. It doesn't say what to fix. And when it reads 7 next week you cannot tell whether the agent improved or the judge was in a better mood. Decompose. Whatever you meant by "quality," write out the handful of separate things you were actually grading, and make each one verifiably TRUE or FALSE. Four binaries beating one 7/10, for three reasons: 1. Each is independently checkable by a human, so you can ALIGN it (next slide). 2. Each becomes its own column, so a regression tells you WHICH property broke. 3. The aggregate is now something you designed, not something a model invented. Binary also makes DISAGREEMENT MEASURABLE. Two reviewers will argue forever about 6 versus 7, and that noise goes into your labels and then into your judge. Ask them "did it cite a source?" and they either agree, or you have a definition problem worth finding. IF YOU GENUINELY NEED A SCALE: every point must name a concrete, observable thing, so two people reading the same output land on the same number. The reading-level example works because each rung is a recognizable artifact: 1 first-grade / 2 fifth-grade / 3 high-school / 4 college / 5 PhD Compare that to what everyone actually ships: "1 = bad ... 10 = good." What is a 6? Nobody can say, which means the numbers aren't comparable between reviewers, between runs, or between models. If you cannot write the anchor for each point, you don't have a scale. You have a vibe with a number attached, and it WILL get treated as data.

Module 4 · 10 minutes

Improve

A bug you find twice is a process failure

Close the loop

So the human's job is not authoring the fix; it's reviewing a diff and merging it. THAT IS ALSO THE JUDGMENT CALL. The merge is the gate, and you should keep it. Letting anything auto-merge on green evals is tempting. Don't, not yet, not for anything safety-adjacent. Two reasons: 1. Your evals are an INCOMPLETE PROXY for "good." An optimizer will find the gap between your metric and your intent. This whole workshop exists because our suite had exactly such a gap. 2. The failure is SILENT. A prompt that games your evaluators looks like progress on every chart you have. So: let it find, diagnose, write the fix, and open the PR, that's the expensive part and none of the risk. Reading a one-line prompt diff before merging is not your bottleneck. If Q&A goes to judge alignment or automations, there are appendix slides for both.

Where to go after this. Hamel Husain has published a set of skills for coding agents that pick up roughly where we stop. If today was the 201, that's the 301, and it's free. Fair framing: his material assumes what we spent today building. It starts from a pipeline that already exists and a stream of real traces. Ours is how you get there. They're complementary halves, not competing advice, and where they overlap (code checks before judges, one judge per failure mode, binary not Likert, domain experts in the loop) they agree, which is worth saying out loud. THREE THINGS HE GOES DEEPER ON: 1. SYNTHETIC DATA, structured. We hand-wrote our dataset, fine for twelve cases, doesn't scale to a hundred. His method: pick three dimensions where you expect failures, generate tuples, then a SEPARATE prompt turns each tuple into a query. Two steps, because doing it in one produces repetitive phrasing. This is how you pressure-test before you have users. 2. ERROR ANALYSIS. The honest gap in today's session. We handed you four online evaluators (out-of-scope, hallucination, perceived error, completion) and I picked those by thinking about it. His process derives them from evidence: read ~100 traces, note the FIRST thing that went wrong in each, let the categories EMERGE rather than starting from a list, group into five to ten, label everything, then rank by frequency and impact. Do that and your evaluator set is grounded in your actual failures instead of borrowed from a paper. He also has a triage step we skipped: before building an evaluator, ask whether you can just FIX it. Missing instruction in the prompt, missing tool, plain bug. Only build an evaluator for what survives the fix. 3. JUDGE ALIGNMENT, properly. We said "label 20 examples and iterate." He's right that that leaks, if you iterate against the same examples you drew few-shots from, your alignment number is inflated. Proper version: train / dev / test split, and measure TPR and TNR rather than raw agreement, because with class imbalance a judge that always says Pass scores 90% and catches nothing. And the one worth knowing about even if you do nothing else: Rogan-Gladen bias correction. If your judge is TPR 0.92, TNR 0.88, and it scores 80% of production traffic as Pass, the TRUE rate is about 85%. That's the dashboard from Module 3 , those numbers are biased in a knowable, correctable direction. Note it matters for ABSOLUTE rates. Our bake-off compared two models under one judge, and relative comparison under a fixed judge is the case that's already trustworthy. There's an eval-audit skill that runs a diagnostic across six areas. Good first thing to point an agent at once you have a pipeline worth auditing.

Automations are filter + sampling rate + action. Four actions: add to dataset, add to annotation queue, trigger webhook, extend retention. Rule 1 routes everything your online evaluators flagged. Obvious, and NOT SUFFICIENT. It can only surface failure modes you already wrote an evaluator for. Exactly the same blind spot as your offline suite. Rule 2 samples 5% of everything, unconditionally, no filter. That's your ONLY channel for finding the failure nobody has named yet. It feels wasteful right up until it surfaces something, and then it's the most valuable rule you have. THE LINE: if you only review what your filters catch, your filters define the ceiling on what you can learn. Practical: rules poll independently, so nothing guarantees an evaluator ran before a webhook fires. Put a filter on the downstream rule. And rules have a Logs tab, use it when a rule "isn't working", because usually it is and the filter doesn't match what you think.

Align your judge

85%

agrees with a human

We've been trusting LLM judges. Should we? An unaligned judge is worse than no judge: it produces confident numbers you act on. Measure it the only way you can, against HUMAN LABELS. Select scored runs -> label ~20 yourself, balanced between pass and fail -> test the evaluator prompt in the Evaluator Playground -> get an alignment score -> refine. WHAT ACTUALLY MOVES THE NUMBER: - Read the misaligned cases and GROUP them. Failure modes cluster; two or three explain most of the gap. - Put the failure modes in the prompt. Domain knowledge the judge lacks. - Add more labels before celebrating. 100% on 20 examples is overfitting. Careful: evaluator prompt edits are NOT saved by default. THE AUTOMATIC VERSION: add {{Few-shot examples}} to the judge prompt. Every score you CORRECT in the UI gets inserted as a few-shot example. Attach an explanation to every correction, that's what teaches it. A judge that improves as a side effect of people using the product, with no engineering time at all.
